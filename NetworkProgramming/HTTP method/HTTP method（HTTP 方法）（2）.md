## 三、GET vs POST 深度对比

### 3.1 为什么 HTTP 规范说 GET 比 POST "更安全"？

这源于 **HTTP 协议规范（RFC 7231）**对"安全方法"的严格定义：

> **安全方法 = 不修改服务器端资源状态、只用于信息获取的方法。**

|维度|GET|POST|
|---|---|---|
|核心语义|**只读**——获取资源|**写入**——提交/创建资源|
|调用 1 次 vs 10000 次|服务器数据完全不变|可能创建 10000 条记录|
|规范结论|✅ **安全**（无副作用）|❌ **不安全**（改变状态）|

> ⚠️ **关键提醒**：这里的"安全"是指**对服务器数据的"只读保护"**，和日常口语中"防黑客/防窃听"完全不是一回事。后面会详细展开这个极易混淆的概念。

### 3.2 全方位区别对比

|对比维度|GET|POST|
|---|---|---|
|**核心语义**|获取/查询资源（读）|创建/提交资源（写）|
|**HTTP 规范安全性**|✅ 安全（只读，无副作用）|❌ 不安全（改变服务器状态）|
|**幂等性**|✅ 幂等（多次请求效果相同）|❌ 非幂等（多次提交可能创建多个资源）|
|**参数位置**|附加在 **URL（Query String）** 中|放在 **请求体（Body）** 中|
|**数据长度限制**|受限于 URL 长度（浏览器/服务器实现限制）|理论上无限制（受服务器配置约束）|
|**数据类型**|通过 URL 编码可传输任意字节，但实践中多用于简单文本|支持任意数据类型（二进制、文件上传等）|
|**可见性**|URL 完全可见，显示在地址栏|参数在 Body 中，地址栏不可见|
|**书签与分享**|✅ 可收藏为书签，可直接分享链接|❌ 无法收藏和分享（Body 无法保存）|
|**回退/刷新**|无害，浏览器可安全重新请求|⚠️ 浏览器通常会弹窗提示"是否重新提交"|
|**缓存机制**|✅ 默认可被浏览器、CDN、代理缓存|❌ 默认不可缓存（需手动配置响应头）|
|**历史记录**|URL 及参数会保存在浏览器历史中|仅保存 URL，不保存 Body 参数|
|**隐私泄露风险**|❌ **高**——参数进 URL，到处留痕|⚠️ **较低**——Body 不进历史/日志（但仍可抓包）|

## 四、其他易混淆方法对比

### 4.1 PUT vs PATCH——最容易搞混的一对

这是实际开发中**混淆率最高**的一组，连不少资深开发者都会用错。

|对比维度|PUT|PATCH|
|---|---|---|
|**核心语义**|**全量替换**目标资源|**部分修改**目标资源|
|**请求体内容**|必须包含资源的**完整表示**（所有字段）|只包含**需要变更的字段**|
|**未提供的字段**|会被**清空/重置**为默认值|**保持不变**|
|**幂等性**|✅ 幂等（同一请求执行多次，结果一致）|❌ 通常非幂等（取决于补丁格式）|
|**资源不存在时**|可以创建新资源（"upsert"语义）|通常返回 404（不创建）|

**具体例子：**

假设用户资料为 `{ "name": "Alice", "email": "alice@example.com", "age": 25 }`

- **PUT** 请求体 `{ "name": "Bob" }` → 结果变为 `{ "name": "Bob", "email": null, "age": null }`（其他字段被清空）
- **PATCH** 请求体 `{ "name": "Bob" }` → 结果变为 `{ "name": "Bob", "email": "alice@example.com", "age": 25 }`（只改 name）

> 💡 **记忆口诀**：PUT = "我重新告诉你整张表的内容"；PATCH = "我只告诉你哪里要改"。

**PATCH 幂等性的特殊情况：**

PATCH 的幂等性取决于补丁格式。使用 RFC 7396（JSON Merge Patch）时，同样的补丁多次执行结果一致，可以认为是幂等的；但使用 JSON Patch（RFC 6902）时，如果补丁中包含"递增"类操作，多次执行结果不同，则非幂等。因此 RFC 5789 没有将 PATCH 统一定义为幂等方法。

### 4.2 PUT vs POST——创建资源时该用哪个？

|对比维度|POST|PUT|
|---|---|---|
|**谁来分配资源 ID**|**服务器**决定（`POST /users` → 返回 `Location: /users/123`）|**客户端**决定（`PUT /users/123`）|
|**幂等性**|❌ 非幂等（多次调用创建多个资源）|✅ 幂等（同一请求多次执行结果一致）|
|**典型场景**|提交表单、创建评论、上传文件|已知 ID 的精确更新或"upsert"|

**实际判断标准：**

- 你**不知道**资源 ID，让服务器生成 → 用 **POST**
- 你**知道**资源 ID，要精确放到某个位置 → 用 **PUT**

```
POST /articles          → 服务器创建文章，返回 ID=42
PUT  /articles/42       → 客户端指定 ID=42，完整替换该文章
```

### 4.3 HEAD vs GET——容易被忽视的"轻量版"

|对比维度|GET|HEAD|
|---|---|---|
|**响应内容**|返回状态行 + 头部 + **完整消息体**|只返回状态行 + 头部，**无消息体**|
|**核心用途**|获取资源内容|探测资源元信息（不下载内容）|

**HEAD 的典型使用场景：**

- **检查资源是否存在**：避免下载大文件后再发现 404
- **获取文件大小**：通过 `Content-Length` 头部判断，决定是否下载
- **检查缓存是否过期**：通过 `Last-Modified` / `ETag` 判断本地缓存是否仍有效
- **链接可用性检测**：爬虫验证外部链接是否仍然有效

> 💡 可以把 HEAD 理解为 GET 的"预检"——先看一眼值不值得下载。

### 4.4 DELETE 的幂等性——为什么"删了再删"也算幂等？

很多人疑惑：第一次 DELETE 返回 200，第二次返回 404，响应都不同了，怎么算幂等？

**关键理解：幂等性看的是"资源状态"，不是"响应码"。**

|操作次数|资源状态|响应码|幂等？|
|---|---|---|---|
|第 1 次 DELETE|资源被删除 ✅|200 OK|—|
|第 2 次 DELETE|资源仍然不存在 ✅|404 Not Found|✅|
|第 100 次 DELETE|资源仍然不存在 ✅|404 Not Found|✅|

无论执行多少次 DELETE，资源的**最终状态**都是"不存在"——这就是幂等。响应码不同不影响幂等性判断。

### 4.5 OPTIONS——CORS 背后的"侦察兵"

OPTIONS 在日常开发中出镜率不高，但一旦涉及**跨域请求**就绕不开它。

**工作流程：**

```
浏览器 → OPTIONS /api/users  （预检：你支持哪些方法？允许哪些头？）
服务器 → Allow: GET, POST, PUT
        Access-Control-Allow-Methods: GET, POST, PUT
        Access-Control-Allow-Origin: https://example.com
浏览器 → POST /api/users      （预检通过后，才发送真正的请求）
```

- 浏览器在发送"非简单请求"（如带 `Authorization` 头、或 `Content-Type: application/json`）之前，会**自动**先发一个 OPTIONS 请求。
- 开发者通常不需要手动调用 OPTIONS，但配置 CORS 时必须正确响应它。

## 五、5 大常见误区

### ❌ 误区一：POST 比 GET 更安全，因为参数看不见（防窃听）

**真相：极其危险的误解！**

- **传输层面**：无论是 GET 还是 POST，在纯 HTTP 下都是**明文传输**。GET 参数在 URL 里，POST 参数在 Body 里，但通过抓包工具（Wireshark、Fiddler）或中间人攻击，**两者都能被完全窃取**。
- **真正的传输安全**靠的是 **HTTPS（TLS 加密）**，不是靠选择 POST。
- **POST 相对"好一点"的地方**：GET 的参数会明文出现在 URL 中，因此会被记录在**浏览器历史、服务器 Access Log、Referer 请求头**里。POST 的 Body 不会进这些地方，隐私泄露风险稍低——但这叫**"隐私保护"**，不叫**"传输安全"**。

> 🔗 _下一节会详细展开 GET 参数暴露的隐私风险。_

### ❌ 误区二：GET 有长度限制，POST 没有

**真相：HTTP 协议本身没有规定 URL 或 Body 的长度限制。**

- GET 的"长度限制"来自**浏览器和 Web 服务器的实现限制**（如老版 IE 限制 2083 字符，Nginx 的 `large_client_header_buffers` 可配置）。
- POST 也不是无限长，同样受服务器配置约束（如 PHP 的 `post_max_size`、Nginx 的 `client_max_body_size`）。

### ❌ 误区三：GET 请求不能带请求体（Body）

**真相：技术上可以发送，但强烈不建议！**

- 用 AJAX 或 cURL 可以给 GET 加 Body，但 **RFC 7231 明确指出 GET 的 Body 没有定义语义**。
- 大多数服务器、代理、CDN、防火墙会**直接忽略** GET 请求中的 Body。需要传输复杂数据时，请使用 POST。

### ❌ 误区四：POST 不会被浏览器记录在历史中

**真相**：浏览器历史记录的是 **URL**，不是整个请求。

- GET：完整 URL（含参数）留在历史里。
- POST：URL 部分也会留在历史里，只是 Body 参数不会显示。

### ❌ 误区五：用 GET 做删除/修改操作没关系，只要不暴露就行

**真相**：违反 HTTP 语义约定，极易引发 **CSRF（跨站请求伪造）** 漏洞。

- 如果用 `GET /delete?id=1`，攻击者只需放一个隐藏图片 `<img src="https://yoursite/delete?id=1">`，用户浏览页面时数据就被悄无声息地删除了。
- 搜索引擎爬虫扫描 URL 也可能误触发操作。**任何改变服务器状态的操作，都必须使用 POST/PUT/DELETE/PATCH。**

## 六、GET 参数暴露在 URL 中的隐私风险

### 6.1 这个问题真实存在且很严重

GET 参数出现在 URL 里，会沿以下路径产生**隐私泄露**：

|泄露渠道|具体场景|
|---|---|
|**浏览器历史**|搜索记录、查看过的敏感页面完整保留|
|**服务器 Access Log**|Nginx/Apache 日志完整记录请求行，包括 `?token=xxx&password=yyy`|
|**Referer 请求头**|页面中点击外链时，当前页面的完整 URL（含参数）会作为 Referer 发送给第三方网站|
|**公司/运营商代理**|内网代理、VPN 日志能看到完整 URL|
|**截图/分享**|把带 `?sessionid=abc123` 的地址栏截图发到群里，直接泄露凭证|

### 6.2 两个"安全"定义的根本区别

|语境|"安全"的含义|GET|POST|
|---|---|---|---|
|**HTTP 协议规范**|不修改服务器数据（只读）|✅ 安全|❌ 不安全|
|**日常隐私语境**|敏感信息不会被轻易泄露|❌ 不安全|⚠️ 相对好一点|

**打个比方：**

> - **GET** 像在**明信片**上写字——邮局（服务器）、邮递员（代理）都能看到内容，但明信片本身不会弄丢东西（只读，不改状态）。
> - **POST** 像把信装进**信封**——外面看不到内容，但信可能要求收件人转账（改状态）。
> - **HTTPS** 是给整封信/明信片套上**装甲运钞车**——路上谁都看不到。

**结论：**

- 协议层面：GET "安全" ✅（不改数据）
- 隐私层面：GET "不安全" ❌（参数到处留痕）

**两个说法都对，只是说的不是同一件事。**

## 七、工程实践建议

### 7.1 场景选型速查

|场景|正确选择|原因|
|---|---|---|
|搜索关键词 `?q=苹果`|**GET**|关键词不敏感，且需要可分享、可缓存|
|翻页 `?page=2`|**GET**|同上|
|登录提交用户名密码|❌ **绝对不用 GET**|密码进 URL = 进日志 = 进历史 = 进 Referer|
|Token/Session 传递 `?token=abc123`|❌ **绝对不用 GET**|同上，且 URL 容易被截图分享|
|提交订单、支付|**POST**|敏感 + 改状态，双重理由|
|文件上传|**POST**（`multipart/form-data`）|GET 无法传输二进制文件|
|完整更新一条记录|**PUT**|幂等，语义清晰|
|部分更新某字段|**PATCH**|只传变更字段，节省带宽|
|删除资源|**DELETE**|幂等，语义明确|

### 7.2 RESTful API 方法选择参考

在实际 API 设计中，HTTP 方法的语义应与 CRUD 操作对应：

|CRUD 操作|HTTP 方法|幂等|说明|
|---|---|---|---|
|**C**reate（创建）|**POST**|❌|服务器分配资源 ID，多次调用创建多个资源|
|**R**ead（读取）|**GET**|✅|只读，可缓存|
|**U**pdate（全量更新）|**PUT**|✅|提交完整资源表示，幂等替换|
|**U**pdate（部分更新）|**PATCH**|❌ 通常|只提交变更字段，具体幂等性取决于补丁格式|
|**D**elete（删除）|**DELETE**|✅|幂等，多次删除结果一致|

### 7.3 不得不在 GET 中传递敏感信息时的防护措施

某些场景（如 OAuth 2.0 授权码回调）协议层面要求通过 URL 传参，此时至少要落实以下防护：

1. **强制 HTTPS**——这是基础中的基础，杜绝明文传输。
2. **响应头设置 `Cache-Control: no-store`**——防止浏览器缓存带敏感参数的 URL。
3. **敏感凭证优先放 `HttpOnly + Secure` Cookie 或 `Authorization` Header**——避免出现在 URL 中。
4. **防 Referer 泄露**——在页面中添加 `<meta name="referrer" content="no-referrer">` 或设置响应头 `Referrer-Policy: no-referrer`，阻止完整 URL 随外链请求泄露给第三方。
5. **授权码设置短有效期**——OAuth 授权码应一次性使用且有效期极短（如 10 分钟），即使泄露也可降低风险。

## 总结

> **HTTP 规范说 GET "安全"，因为它不会改你的数据库。**
> 
> **同时 GET "也不安全"，因为它把参数到处留痕，隐私风险极高。**
> 
> **两个说法都对，只是维度不同。**
> 
> **实际开发中，牢记两条铁律：敏感信息永远不用 GET 传递，改变数据的操作永远不用 GET 执行。**
