## 核心方法（HTTP/1.1 + 常见扩展）

这些是互联网工程任务组（IETF）在 RFC 7231、RFC 5789 等文档中定义的最基础和最广泛使用的方法。

| 方法           | 描述                                             | 典型用途                                    |
| ------------ | ---------------------------------------------- | --------------------------------------- |
| **GET**​     | 请求指定的资源。只应读取数据，不应产生副作用。                        | 获取网页、查询数据。                              |
| **HEAD**​    | 与 GET 相同，但服务器只返回状态行和头部，不返回消息体。                 | 检查资源是否存在、获取文件大小（Content-Length）或最后修改时间。 |
| **POST**​    | 向指定资源提交数据，请求服务器进行处理（如创建或更新）。通常**非幂等**。         | 提交表单、上传文件、创建新资源（服务器分配ID）。               |
| **PUT**​     | 将请求的有效载荷**完整替换**目标资源。如果资源不存在则创建。是**幂等**的。      | 更新用户资料（需提交完整字段）。                        |
| **PATCH**​   | 对资源进行**部分修改**（RFC 5789）。只发送需要变更的字段。通常**非幂等**。  | 仅修改用户的邮箱，而不提交其他字段。                      |
| **DELETE**​  | 删除指定的资源。是**幂等**的（即使已删除，再次删除也不报错或返回404）。        | 删除一篇文章、注销账户。                            |
| **CONNECT**​ | 将请求连接转换为透明的 TCP/IP 隧道，通常用于 SSL 通过代理的 HTTPS 连接。 | 代理服务器建立隧道。                              |
| **OPTIONS**​ | 返回目标资源支持的 HTTP 方法。常用于跨域（CORS）预检请求。             | 查询 API 端点支持哪些操作。                        |
| **TRACE**​   | 回显客户端请求，主要用于诊断。因存在跨站追踪（XST）安全风险，通常被禁用。         | 调试请求链路。                                 |

## 关键属性速查表

理解这三个属性对于构建安全、可缓存和可靠的 API 至关重要：

|方法|安全 (Safe)|幂等 (Idempotent)|可缓存 (Cacheable)|
|---|---|---|---|
|**GET**​|✅ 是|✅ 是|✅ 是|
|**HEAD**​|✅ 是|✅ 是|✅ 是|
|**POST**​|❌ 否|❌ 否|⚠️ 仅当响应包含 Freshness 信息时|
|**PUT**​|❌ 否|✅ 是|❌ 否|
|**PATCH**​|❌ 否|❌ 否|❌ 否|
|**DELETE**​|❌ 否|✅ 是|❌ 否|
|**OPTIONS**​|✅ 是|✅ 是|❌ 否|
|**TRACE**​|✅ 是|✅ 是|❌ 否|
|**CONNECT**​|❌ 否|❌ 否|❌ 否|

> **名词解释：**
> 
> - **安全方法**：不修改服务器端资源状态（仅用于读取）。GET、HEAD、OPTIONS、TRACE 是安全的。
> - **幂等方法**：客户端发起一次或多次相同请求，对服务器产生的副作用与单次请求完全相同。PUT 和 DELETE 是幂等的，即使资源已被删除，再次 DELETE 也不会造成额外状态变化。
> - **可缓存**：响应可以被客户端或代理缓存，以减少服务器负载和带宽。



## 为什么在 HTTP 规范中 GET 比 POST “更安全”？

在 HTTP 协议语境下，**“安全方法（Safe Method）”的定义是：不修改服务器端资源状态、只用于信息获取的方法。**

- **GET 是“安全”的**：它的语义是**只读**。无论你调用一次还是一万次 GET 请求，服务器上的数据都不会发生任何变化（不会产生副作用）。比如你刷新一个网页 100 次，文章不会消失。
- **POST 是“不安全”的**：它的语义是**提交/创建**。调用 POST 请求通常会导致服务器状态改变，比如新建了一个订单、扣了一笔钱、发了一篇文章。

> 💡 **结论**：这里的“安全”是指**对服务器数据的“只读保护”**，而不是指防止数据被窃取。

## GET 与 POST 全方位区别对比

| 对比维度            | GET                          | POST                   |
| --------------- | ---------------------------- | ---------------------- |
| **核心语义**​       | 获取/查询资源（读）                   | 创建/提交资源（写）             |
| **HTTP 规范安全性**​ | ✅ **安全**（只读，无副作用）            | ❌ **不安全**（改变服务器状态）     |
| **幂等性**​        | ✅ **幂等**（多次请求效果相同）           | ❌ **非幂等**（多次提交会创建多个资源） |
| **参数位置**​       | 附加在 **URL（Query String）**​ 中 | 放在 **请求体（Body）**​ 中    |
| **数据长度限制**​     | 受限于 URL 长度（浏览器/服务器限制）        | 理论上无限制（受服务器配置限制）       |
| **数据类型**​       | 只允许 ASCII 字符                 | 支持任意数据类型（二进制、文件等）      |
| **可见性**​        | URL 完全可见，会显示在地址栏             | 参数在 Body 中，地址栏不可见      |
| **书签与分享**​      | ✅ 可收藏为书签，可直接分享链接             | ❌ 无法收藏和分享（Body 无法保存）   |
| **回退/刷新**​      | 无害，浏览器可安全重新请求                | ⚠️ 浏览器通常会弹窗提示“是否重新提交”  |
| **缓存机制**​       | ✅ 默认可被浏览器、CDN、代理缓存           | ❌ 默认不可缓存（需手动配置响应头）     |
| **历史记录**​       | URL 及参数会保存在浏览器历史中            | 仅保存 URL，不保存 Body 参数    |

## 关于 GET 和 POST 的 5 大常见误区

### ❌ 误区一：POST 比 GET 更安全，因为参数看不见（防窃听）

**真相**：**极其危险的误解！**

- **传输层面**：无论是 GET 还是 POST，在纯 HTTP 协议下都是**明文传输**。GET 参数在 URL 里，POST 参数在 Body 里，但通过抓包工具（如 Wireshark、Fiddler）或中间人攻击，**两者都能被完全窃取**。
- **真正的安全**靠的是 **HTTPS（TLS 加密）**，而不是靠 POST。
- **POST 相对“好一点”的地方**：GET 的参数会明文出现在 URL 中，因此会被记录在**浏览器历史记录、服务器 Access Log 日志、Referer 请求头**里。所以敏感信息（如密码、Token）用 GET 会留下痕迹，POST 在这方面隐私泄露风险稍低，但这叫“隐私保护”，不叫“传输安全”。

### ❌ 误区二：GET 有长度限制，POST 没有

**真相**：**HTTP 协议本身没有规定 URL 或 Body 的长度限制。**

- GET 的所谓“长度限制”，其实是**浏览器和 Web 服务器**的限制。例如老版 IE 限制 URL 为 2083 字符，Nginx 默认限制 URL 较长（可配置）。
- POST 也不是无限长，它受限于服务器的配置（如 PHP 的 `post_max_size`，Nginx 的 `client_max_body_size`）。

### ❌ 误区三：GET 请求不能带请求体（Body）

**真相**：**技术上可以，但强烈不建议！**

- 在技术上，你可以用 AJAX 或 cURL 给 GET 请求加上 Body（如 `curl -X GET -d '{"id":1}'`）。
- 但 **RFC 规范明确说明 GET 的 Body 没有语义**，大多数服务器、代理、CDN 和防火墙会**直接忽略 GET 请求中的 Body**。如果你试图用 GET 传复杂数据，大概率服务器收不到。

### ❌ 误区四：POST 不会被浏览器记录在历史中

**真相**：浏览器历史记录的是 **URL**，而不是整个请求。

- GET 请求的完整 URL（包含参数）会留在历史里。
- POST 请求的 **URL 部分**也会留在历史里，只是 Body 里的参数不会显示在历史记录中。

### ❌ 误区五：用 GET 做删除/修改操作没关系，只要不暴露就行

**真相**：这违反了 HTTP 语义，且极易引发**跨站请求伪造（CSRF）**漏洞。

- 如果你用 GET 来删除数据（`GET /delete?id=1`），那么只要用户点击一个隐藏的图片标签 `<img src="https://yoursite/delete?id=1">`，数据就会被悄无声息地删除。
- 搜索引擎爬虫或预加载插件扫描 URL 时，也可能误触 GET 接口导致数据被改。因此，**任何改变数据的操作都必须用 POST/PUT/DELETE**。
